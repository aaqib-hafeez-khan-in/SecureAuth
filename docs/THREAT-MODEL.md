# SecureAuth Threat Model

## 1. Security scope

SecureAuth is a local Android TOTP authenticator. It does not currently implement a backend identity provider, remote account database, password authentication service, HTTP API, or server-side session/token system.

The primary security asset is the user's TOTP secret. The application uses Android Keystore to protect an AES-GCM key used to encrypt that secret before it is stored in app-private SharedPreferences.

## 2. Security boundaries

### User boundary

The user is trusted to enter a legitimate TOTP secret and to operate the application on a device they control. The application must not expose the stored secret through normal UI behavior after it has been saved.

### Application boundary

SecureAuth runs as an Android application in its own application sandbox. Application code can access the locally stored encrypted secret and account label through the app's storage APIs.

### Device boundary

The Android operating system, application sandbox, and Android Keystore are treated as trusted platform components. The current design relies on the device's security controls to protect the Keystore key and app-private storage.

### Keystore boundary

The AES key is generated in the Android Keystore under the `secureauth_totp_key` alias. The application uses that key for AES-GCM encryption and decryption; the raw key material is not stored in SharedPreferences.

### Storage boundary

The encrypted TOTP secret, initialization vector, and account label are stored in app-private SharedPreferences. The secret is encrypted before persistence, while the account label is stored as ordinary application data.

### External service boundary

There is no backend or network service in the current implementation. TOTP generation is performed locally from the stored secret and the device clock.

## 3. Authentication and authorization model

SecureAuth is an authenticator rather than a conventional user-account authentication service.

- There is no server-side user registration flow.
- The `Login` and `Register` activities currently provide UI shells only; they do not authenticate a user or create an account.
- There is no password credential store.
- There is no bearer access token, refresh token, cookie session, or server-side session state.
- There are no application roles or permission checks.
- Access to the stored TOTP secret is governed by the Android application sandbox and the device security model rather than by an application-level authorization service.

The TOTP code generated by SecureAuth is itself an authentication factor intended for use with an external service. SecureAuth does not validate that code against an external identity system.

## 4. Current data flow

1. The user enters an account label and Base32 TOTP secret.
2. The secret is validated by generating a TOTP value locally.
3. SecureAuth obtains or creates an AES key in Android Keystore.
4. The secret is encrypted with AES-GCM using a fresh initialization vector.
5. The encrypted secret and IV are persisted in app-private SharedPreferences.
6. On restart, the encrypted secret is decrypted locally through the Keystore-backed key.
7. TOTP codes are generated locally and displayed without repopulating the secret field.
8. Account deletion clears the local SharedPreferences data.

## 5. Threats considered

| Threat | Current control | Residual limitation |
| --- | --- | --- |
| TOTP secret exposed in plaintext storage | AES-GCM encryption with Android Keystore-backed key | Compromise of the running app/device can still expose plaintext to the app process |
| Secret accidentally displayed after restore | Secret input is cleared after restore | Future UI changes must preserve this property |
| Reuse of a static encryption IV | Fresh random 12-byte IV per save | Existing data has no additional authenticated metadata beyond GCM's authentication tag |
| Unauthorized access by another normal app | Android application sandbox and app-private storage | A compromised/rooted device is outside the normal trust model |
| Network interception | No network path for TOTP secrets or generated codes | No remote synchronization or recovery exists |
| Loss of device/app data | None | TOTP secrets cannot currently be recovered from a cloud backup |
| Misleading authentication UI | Login/Register are not treated as working authentication | These screens should not be represented as real account authentication until implemented |

## 6. Assumptions

- The Android platform and Keystore implementation are trusted.
- The device is running a supported Android environment with functioning application sandboxing.
- The user protects the physical device and its unlock credentials.
- The device is not intentionally rooted or compromised at the operating-system level.
- The user does not enter real TOTP secrets into an untrusted build of the application.
- The device clock is sufficiently accurate for RFC 6238 TOTP generation.

## 7. Current limitations

- There is no user authentication layer protecting the app itself.
- There is no biometric or device-credential gate implemented by SecureAuth before revealing generated codes.
- There is no multi-account model; the current storage implementation represents one active account.
- There is no encrypted backup or recovery mechanism.
- There is no remote synchronization.
- The Android manifest currently allows backup, so backup behavior requires explicit security review before production use.
- Login and Register activities are present but are not functional authentication mechanisms.
- Security behavior has not yet been comprehensively validated against a production threat model.

## 8. Phase boundaries

This document establishes the baseline for the later security phases. It intentionally does not implement password hardening, token/session lifecycle controls, authorization enforcement, rate limiting, API security, or expanded security regression testing. Those concerns remain separate phases in Epic #8.
